Self-declared limitations (verbatim):

> **Read these numbers honestly.** MAE of 0.24 cm is *not* real-world accuracy. The "gauge" the model
> learned from is a deterministic reservoir whose noise is `rng.normal(0.0, 0.18)` — the model is
> predicting a near-deterministic function of rainfall, which is why error is so small and why the
> persistence baseline is so weak (a smooth synthetic series is close to a random walk).

## 9. Runtime-generated data (created by the running system, not shipped)

### 9a. `telemetry_readings` — one row per accepted reading
Written by `telemetry.py:ingest_telemetry_reading`. Carries a **risk snapshot on the row itself**
(`risk_level`, `risk_score`) so a reading is interpretable without a join.

### 9b. `risk_assessments` — one row per reading (horizon 0)
Component columns store the **normalised** 0–1 values, not the weighted contributions
(`telemetry.py:128-144` comment: "normalized component scores (0-1) — not scenario contribution units").

### 9c. `forecasts` — 3 rows per cycle per node
`made_at` (when predicted), `target_time` (when it applies), `horizon_minutes` ∈ {15,30,60},
`predicted_level_cm`, `lower/upper_bound_cm`, `input_source`, `status`.
Bounds are **hard-coded ±10 cm** (`forecast_service.py:280-281`, `333-334`) — not a Random-Forest
tree spread, despite `System-Architecture.md:269` proposing one.

### 9d. `flood_layers` — 3 rows per time step (depth, risk, boundary)
`geojson` holds a full `FeatureCollection` in a JSONB column.

### 9e. `flood_impacts` — one row per affected road/building, attached to the `depth` layer.

### 9f. `alerts` — created/updated/cleared by the alert engine.
Note `alerts.created_at` is overwritten on a threshold severity change
(`alert_engine.py:364-366`) so the UI's "N min ago" reflects the last change, not first creation.
