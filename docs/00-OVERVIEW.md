## 1. What this project is

**FLOODGUARD AI** is an IoT-driven flood monitoring, prediction and 3D-visualisation system for the
**Mithi River corridor (BKC → Kurla, Mumbai)**.

It is a hackathon build (IIT Bombay, 36–48 h target, per `PRD.md`). The product idea, stated in
`PRD.md:6`:

> "Predict the flood. Visualize the impact. Prepare before disaster strikes."

The intended product shape is:

1. A **real ESP32 hardware sensor** measures water level + rainfall in a miniature channel.
2. The reading is ingested by a Python backend (REST or MQTT).
3. A **trained ML model** predicts water level at +15, +30 and +60 minutes.
4. A **rule-based risk engine** converts readings/forecasts into an explainable risk score.
5. A **flood simulation engine** turns predicted water level into a GeoJSON inundation polygon set on a
   real 30 m DEM.
6. A **React web console** shows it on a command-centre dashboard, a 2D Leaflet map, a 3D WebGL twin,
   a what-if scenario simulator and an alerts page.
7. Every number carries a **provenance label** so simulated data is never shown as live.

## 2. The single most important architectural fact about this build

The live system is **driven by exactly one real input** — a physical ESP32 node registered through
`POST /api/iot/devices/register`. The rest of the corridor is derived from it by a **configurable linear
calibration**, not by a hydraulic model.

`backend/app/core/config.py:93-101` (with the honest comment written by the original author):

```python
# ── Real demo input -> simulated Mithi calibration ───────────────────
# These are configurable demo calibration points, not a geographic or
# hydraulic relationship between Vadodara and Mumbai.
demo_input_physical_min_cm: float = 0.0
demo_input_node_code: str = ""
demo_input_physical_max_cm: float = 30.0
demo_input_mithi_min_cm: float = 118.0
demo_input_mithi_max_cm: float = 220.0
demo_input_mithi_rainfall_factor: float = 0.8
```

The mapping is implemented once in `forecast_service.ForecastService.map_demo_level()`
(`backend/app/services/forecast_service.py:208-217`):

```python
fraction = max(0.0, min(1.0, (physical_level_cm - minimum) / (maximum - minimum)))
return self.settings.demo_input_mithi_min_cm + fraction * (
    self.settings.demo_input_mithi_max_cm - self.settings.demo_input_mithi_min_cm
)
```

So a physical channel reading of `0 → 30 cm` maps linearly onto a Mithi reference level of
`118 → 220 cm`. This is exposed to the UI as a panel titled
**"DEMO CALIBRATION / SIMULATION MAPPING"** (`backend/app/api/flood_monitor.py:309-318`) with the note:

> "Configurable demonstration calibration; not a Vadodara-to-Mumbai hydraulic relationship."

If no recent physical reading exists, the API returns
`simulation_input.status = "waiting"` and every screen prints
**`WAITING FOR REAL IoT INPUT`** rather than inventing numbers
(`backend/app/api/flood_monitor.py:294`, `Frontend/app/page.tsx:152`).

## 4. Five pipelines, end to end

| # | Pipeline | Entry point | Output |
|---|---|---|---|
| 1 | **Offline data prep** | `backend/scripts/preprocess_data.py` | `data/osm/*.geojson`, `data/rainfall/imd/processed/mumbai_rainfall.json` |
| 2 | **Geo load** | `backend/scripts/load_osm_layers.py` | PostGIS `roads` + `buildings` tables |
| 3 | **ML training** | `backend/scripts/train_forecast_models.py` | `models/flood/rf_{15,30,60}min.joblib` + `model_metadata.json` + `model_registry` rows |
| 4 | **Live telemetry → prediction → inundation** | `POST /api/iot/telemetry` or MQTT → `telemetry.py` → `forecast_service` → `mithi_demo_pipeline` → `flood_simulation` → `alert_engine` → Redis → Socket.IO → browser | `telemetry_readings`, `forecasts`, `risk_assessments`, `flood_layers`, `flood_impacts`, `alerts` |
| 5 | **What-if scenario** | `POST /api/scenarios/run` | `scenarios` + `forecasts` + `risk_assessments` + `flood_layers` for that scenario_id |

Each is documented in detail in [`04-DATA-PIPELINES.md`](04-DATA-PIPELINES.md).

## 5. What is AI/ML and what is not

| Component | Type | Where |
|---|---|---|
| Water-level forecasting | **Machine learning** — scikit-learn `RandomForestRegressor`, one model per horizon (15/30/60 min), compared against a persistence baseline and LinearRegression | `models/flood/rf_*.joblib`, trained by `backend/scripts/train_forecast_models.py` |
| Training rainfall forcing | **Real observations** — IMD gridded daily rainfall for 2019, 2023, 2024 | `data/IMD/gridded rainfall {19,23,24}.nc` |
| Training water levels | **SIMULATED** — single-reservoir storage-routing model driven by that rainfall | `train_forecast_models.py:120-169` (`simulate_storage`, `storage_to_levels`) |
| Flood-risk scoring | **NOT ML** — rule-based weighted sum with fixed normalisation | `backend/app/services/flood_risk.py` |
| Flood extent | **NOT ML** — elevation-threshold raster inundation + BFS connectivity mask | `backend/app/services/flood_simulation.py` |
| Scenario projection | **NOT ML** — closed-form linear level-rise formula | `backend/app/services/scenario_service.py:191-208` |
| 3D twin | **NOT ML** — three.js scene with a Gerstner-wave GLSL water shader | `Frontend/components/DigitalTwin.tsx:205-277` |
| LLM usage | **NONE anywhere in the codebase** | — |

Detail: [`05-ALGORITHMS-AND-AI-ML.md`](05-ALGORITHMS-AND-AI-ML.md).
