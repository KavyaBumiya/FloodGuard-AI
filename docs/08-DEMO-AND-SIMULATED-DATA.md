## PART 1 — The four provenance classes the code uses

The backend persists `source` on every reading (`telemetry_readings.source`) and `data_mode` on the
same row:

| `source` | `data_mode` | Meaning |
|---|---|---|
| `iot` | `live` | a real reading from a registered physical device |
| `simulated` | `simulated` | generated by `virtual_sensors.py` |
| `replay` | `replay` | played back from `replay_recordings.payload` |
| `scenario` | `scenario` | a what-if run |

`data_mode_for_source()` (`telemetry.py:49-50`): `return "live" if source == "iot" else source`.

`input_source` on `forecasts` and `flood_layers` takes the same four values **plus one that is not in
the enum**: `"iot-demo"`. That is what the mapped Mithi state is stored under.

## PART 2 — 🟢 REAL, live: the physical ESP32 input

### Where it enters

| Path | Code |
|---|---|
| HTTP POST | `POST /api/iot/telemetry` — `backend/app/api/iot.py:300` |
| HTTPS | `POST /api/iot/telemetry` — `backend/app/api/iot.py` → `backend/app/services/ingest.py` |

Both converge on `telemetry.ingest_telemetry_reading()` (`telemetry.py:68`).

### Registration

```bash
curl -X POST http://127.0.0.1:8000/api/iot/devices/register \
  -H "Authorization: Bearer $IOT_REGISTRATION_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"node_code":"VAD-ESP32-01","name":"Vadodara Demo Sensor","node_type":"physical",
       "lat":22.3072,"lng":73.1812,"reference_elevation_m":1.2,"baseline_level_cm":0,
       "warning_threshold_cm":25,"battery_pct":100}'
# → 201 {"node_code":"VAD-ESP32-01","token":"<shown ONCE>","status":"active"}
```

`IOT_REGISTRATION_TOKEN` comes from `backend/.env` (line 16). Note that the demo calibration
assumes the physical channel reads **0–30 cm** (`DEMO_INPUT_PHYSICAL_MIN_CM=0`,
`DEMO_INPUT_PHYSICAL_MAX_CM=30`).

### Sending a reading

```bash
curl -X POST http://127.0.0.1:8000/api/iot/telemetry \
  -H "Authorization: Bearer <device token>" \
  -H "Content-Type: application/json" \
  -d '{"node_code":"VAD-ESP32-01","water_level_cm":14.5,"rainfall_mm_hr":6.2,
       "timestamp":"2026-10-06T09:15:00+05:30","event_id":"evt-0001",
       "battery_voltage":4.05,"valid":true}'
# → 201 {"id":123,"node_code":"VAD-ESP32-01","status":"accepted",
#         "risk_level":"LOW","risk_score":0.05,"received_at":"..."}
```

### What the live path does with it, in order

1. Validate (`iot.py:311-352`).
2. `ingest_telemetry_reading` → rise rate, risk, insert reading + risk row, update freshness, commit,
   publish 2 Socket.IO envelopes.
3. Because `source == "iot"` → `process_real_demo_input()` (`telemetry.py:202-212`).
4. Map 14.5 cm → `118 + (14.5-0)/(30-0) × (220-118) = 118 + 0.4833 × 102 = 167.3 cm` Mithi.
5. Forecast at +15/+30/+60 (if ≥ 8 historical readings exist).
6. Flood-simulate at 0/15/30/60 and persist 12 `flood_layers` rows + impacts.
7. Publish `flood.mithi.updated`.
8. Within ≤ 30 s the alert engine evaluates the node against the 5 rules.

### Freshness gate

`is_recent_physical_reading()` (`telemetry.py:27-39`) requires `source == "iot"` **and**
`age ≤ DEVICE_STALE_AFTER_MINUTES` (5 min, from `config/risk_thresholds.json`). Mirrored on the
client in `lib/constants.ts:136-144` with a hard-coded 5-minute window.

When the gate fails:
- `GET /api/flood/nodes` → `latest_reading: null`, `current_risk: null`
- `GET /api/flood/forecasts/{code}` → `[]`
- `GET /api/iot/devices/{code}/latest` → **404** `"No recent live IoT telemetry for this device"`
- `simulation_input.status` → `"waiting"`
- Every page prints **`WAITING FOR REAL IoT INPUT`** / **`WAITING FOR SENSOR`** / **`NO LIVE IOT DATA`**

## PART 3 — 🔴 SIMULATED: the Demo Calibration / Simulation Mapping

This is **the** simulated component in the running system. It is a 5-parameter linear rescale, not a
model.

### The parameters (env-overridable)

| Setting | Default | Env var | Where consumed |
|---|---|---|---|
| `demo_input_node_code` | `""` (any physical node) | `DEMO_INPUT_NODE_CODE` | `forecast_service`, `virtual_sensors`, `flood_monitor`, `mithi_demo_pipeline` |
| `demo_input_physical_min_cm` | 0.0 | `DEMO_INPUT_PHYSICAL_MIN_CM` | mapping |
| `demo_input_physical_max_cm` | 30.0 | `DEMO_INPUT_PHYSICAL_MAX_CM` | mapping |
| `demo_input_mithi_min_cm` | 118.0 | `DEMO_INPUT_MITHI_MIN_CM` | mapping |
| `demo_input_mithi_max_cm` | 220.0 | `DEMO_INPUT_MITHI_MAX_CM` | mapping |
| `demo_input_mithi_rainfall_factor` | 0.8 | `DEMO_INPUT_MITHI_RAINFALL_FACTOR` | mapping (virtual engine only) |

### The formula

```
fraction   = clamp((physical_cm − physical_min) / (physical_max − physical_min), 0, 1)
mithi_cm   = mithi_min + fraction × (mithi_max − mithi_min)
```

### Worked table (defaults)

| Physical channel | fraction | Mithi simulated |
|---|---|---|
| 0 cm | 0.000 | 118.0 cm |
| 7.5 cm | 0.250 | 143.5 cm |
| 15 cm | 0.500 | 169.0 cm |
| 22.5 cm | 0.750 | 194.5 cm |
| 30 cm | 1.000 | 220.0 cm |
| 45 cm (clamped) | 1.000 | 220.0 cm |

### Where the simulated value is used

| Consumer | Code |
|---|---|
| `simulation_input.mithi_water_level_cm` | `flood_monitor.py:249-253` |
| Forecast input | `mithi_demo_pipeline.py:54-61` → `generate_mithi_forecasts(…, source="iot-demo")` |
| Step-0 flood simulation | `mithi_demo_pipeline.py:65-66` — `levels[physical_node.id] = mapped_level` |
| Persistence | `Forecast.input_source = "iot-demo"` (`forecast_service.py:282`) |
| Layer persistence | `FloodLayer.input_source = "iot-demo"` (`mithi_demo_pipeline.py:82`) |
| 60 s auto-forecast | `forecast_service.generate_all_forecasts()` → `map_demo_level(latest.water_level_cm)` |
| 3D water height | `DigitalTwin.tsx:62-69` reads `simulationInput.mithi_water_level_cm` |

## PART 4 — 🔴 SIMULATED but NOT RUNNING: the virtual sensor network

`config/virtual_sensors.json` and `backend/app/services/virtual_sensors.py` define a 3-node
simulated network with delay+attenuation propagation. **It is not running.**

### Proof

`main._start_engines()` (`main.py:71-77`) starts exactly:

```python
starters.extend((
    ("forecast_service", forecast_service.start_auto_forecast),
    ("alert_engine", alert_engine.start),
))
```

`virtual_sensor_engine.start()` is never called. A repo-wide search for `virtual_sensor_engine`,
`seed_virtual_network` and `generate_now` returns hits **only inside `virtual_sensors.py`**.

### Consequences

| Item | Status |
|---|---|
| `MITHI-SIM-01/02/03` rows in `sensor_nodes` | **Never created** (`seed_virtual_network()` is not called) |
| `node_relationships` rows | **Never created** |
| `simulated` telemetry rows | **Never produced** |
| `/api/flood/nodes` | Filters to `node_type == "physical"` anyway, so virtual nodes would be invisible even if they existed |
| `/data` page claim | *"No virtual sensor network is active. The live application waits for the registered physical IoT input."* — **this is accurate** |
| `PRD.md:196` claim | *"the application does not create virtual sensor telemetry in live mode"* — **also accurate** |

So the PRD and the UI text were deliberately updated to match the code, and the engine remains as
unused reference implementation. The consequence for a demo is simply that the console shows **one
node**, and the Mithi corridor exists only as the mapped simulation, the flood layers and the 3D
scene.

## PART 5 — 🔴 SIMULATED training data

### The synthetic water-level series

Generated entirely in memory by `backend/scripts/train_forecast_models.py`. No file is written.

| Stage | Function | Nature |
|---|---|---|
| Daily → 5-min intensity | `build_subdaily_rainfall` (line 93) | **shape** is invented (gamma × late-afternoon diurnal); **daily totals are the real IMD values** |
| Rain → storage | `simulate_storage` (line 120) | nonlinear-reservoir routing with a soil store |
| Storage → stage (cm) | `storage_to_levels` (line 144) | percentile-relative normalisation + concave curve + EMA lag + N(0, 0.18) noise |

The header of `train_forecast_models.py:3-11` states the contract:

> *REAL:* the rainfall forcing series comes from the IMD gridded files … *SIMULATED:* the 5-minute
> water-level series is generated by a documented single-reservoir (storage-routing) model driven by
> that rainfall. The project has no year of 5-minute gauge records, so training levels must be
> synthesised. Every artefact and every metric written by this script is labelled accordingly.

That label is carried into:
- `bundle["level_source"]` in each `.joblib`
- `model_metadata.json → level_source`
- the `ModelRegistry.training_data_description` string (which `/api/about/model-info` returns and
  `/prediction` prints as its `caveat`)
- the `model_metadata.json → limitations` array

### The orphaned CSV

`data/ml/synthetic_water_levels.csv` (105,120 rows, 5-min cadence, 2024-01-01 → 2024-12-30,
`source = synthetic`) — **referenced by zero lines of code**. It appears to be an earlier export from
a previous training approach that the shipped `train_forecast_models.py` replaced. Safe to delete.

## PART 6 — 🔴 SIMULATED: scenario projections

`scenario_service._generate_scenario_forecasts()` produces, for **every active node**, four forecast
rows per run, all tagged `input_source = "scenario"` and `scenario_id = <id>`.

```
effective_rain = rainfall_mm_hr × (1 − drainage_pct/100) × 0.70
rise_per_min   = effective_rain × 0.84 / 60
level(h)       = min(initial_level_cm + rise_per_min × h, 300)
```

No randomness. Fully deterministic. The assumptions are printed verbatim on `/scenarios` and are
stored in `scenarios.assumptions` (JSONB), so a stored scenario carries its own provenance.

Scenario contamination is prevented by every read path filtering `scenario_id IS NULL` for live data:
`/api/flood/nodes` (forecasts), `/api/flood/forecasts/{code}`, `/api/flood/impact-summary`,
`/api/flood/layers/{step}`, `/api/alerts`, `/api/alerts/active`, `/api/alerts/history`.

## PART 7 — 🔴 REPLAY data

`demo_controller` implements it; nothing is seeded.

| Piece | State |
|---|---|
| `replay_recordings` table | empty on a fresh DB (nothing seeds it) |
| `POST /api/demo/seed` | **no-op** — logs `demo_seed_skipped`, reason `live_input_requires_registered_esp32` |
| `POST /api/demo/recordings?name=X&duration_seconds=300` | captures real telemetry → works once a device has been sending |
| `POST /api/demo/replay/{id}/start?speed=1.0` | replays, re-tagging each reading `source="replay"`, `data_mode="replay"`, through `ingest.ingest_payload()` — **the same pipeline as live HTTPS** |
| UI | `/api/demo/status` sets `mode`, which the `Shell` renders as the amber `REPLAY — Recorded data being replayed — not live conditions.` strip |

`DEMO_MODE_ENABLED=true` and `DEMO_REPLAY_SPEED=1.0` exist in `.env` but `demo_mode_enabled` and
`demo_replay_speed` are **never read** by any code (verified). `demo_controller._replay_speed` is
initialised to `1.0` in the constructor and only changed by `start_replay(speed)`.

### ⚠️ Secret-hygiene warning about `backend/.env`

```
JWT_SECRET=your-super-secret-jwt-key-change-in-production
IOT_REGISTRATION_TOKEN=your-registration-token-here
DATABASE_URL=postgresql+asyncpg://floodguard:floodguard@localhost:5432/floodguard
```

`JWT_SECRET` is unused (there is no JWT code). `IOT_REGISTRATION_TOKEN` **is** the bootstrap secret
gating device registration — `"your-registration-token-here"` is a guessable value and anyone with
network access can register a node. `JWT_ALGORITHM` and `JWT_EXPIRE_MINUTES` are likewise unused.
`backend/.env` is correctly listed in both `.gitignore` and `.dockerignore`, but it currently exists
on disk with placeholder secrets — **change `IOT_REGISTRATION_TOKEN` before exposing the API on a LAN.**
